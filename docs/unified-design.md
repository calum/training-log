# Unified design: one coach, one Home, no data loss

Status: agreed direction (decisions below were confirmed by Calum). Nothing here is built yet. Build in the phases at the end, one small PR each, CI green before merge.

## Why

The Hyrox race plan was added on top of the original weekly-target app, so two coaches exist: `RacePlanner` (race plan) and `WeekPlanner`/`NextUp` (old gym 2 + treadmill 3). Home, Start, the reminder and the "good week" ring each pick one, so the screen can say two different things (seen on 21 Nov: the Hyrox card said "Kick-off: easy aerobic, 30 min, Sun 22 Nov" while NEXT UP said "Treadmill day"). PR #1 fixed that one card; this document fixes the cause.

## Decisions (confirmed)

1. **Good week = plan sessions done.** While a plan is on, the ring, streak, XP and badges count the sessions the plan asked for that week. The old 2 gym / 3 treadmill targets are paused, not deleted (they come back for the maintenance plan only if it uses them).
2. **After the race (Sat 27 Feb 2027) roll into a maintenance plan automatically** (easy weekly plan, about 2 strength + 2-3 aerobic), and offer a new race or block whenever wanted.
3. **Start flow: plan first, free choice second.** Start shows the planned session; the time / energy / knee picker stays below for anything different.
4. **Blocks live inside the plan.** A block is a goal shown on the plan (for example squat 100 kg by a date); it does not schedule sessions. Existing block data is kept.

- Core mat routine, hike timer, Hyrox hub, stations, sessions, simulation mode, knee care and calf ladder, home kit and equipment.

## Design

### 1. One "Today" engine

A single pure function in `core` (working name `Coach.today(records, profile, today)`) returns one value:

- `planned`: today's open planned session, if any;
- `next`: the next open session this week (or next week), with its date;
- `alternatives`: what "I have some time" would offer;
- `mode`: RACE_PLAN, MAINTENANCE or NONE.

Rules:

- With the race plan enabled it delegates to `RacePlanner`. Otherwise (before it is switched on, or after race day) it delegates to the maintenance plan, which is generated by the same planner with no race date, so there is still only one planning engine.
- Home, NEXT UP, Start, "I have some time", the reminder, notifications and any widget only display this value. None plans on its own.
- `WeekPlanner` and `NextUp` stop being used for suggestions. `WeekPlanner`'s remaining jobs (week strip day states, rest-day logic) move to the Today engine or a small `WeekStrip` helper.
- An architecture test fails the build if anything outside the engine calls `WeekPlanner`/`NextUp`/`Recommender` to suggest a session (a source-scan test, same style as the existing flow tests).

### 2. One definition of a good week

`Rewards`/ring/streak/badges take "planned sessions this week and which are done" from the engine instead of `gymTarget`/`treadmillTarget`. No-guilt behaviour is unchanged: a skipped session is never a failure, rest tokens still protect streaks. A migration test proves historical streak, XP and trophies are identical for past weeks (computed from stored records, never rewritten).

### 3. One simple Home

Top to bottom: **Today** hero card (what, minutes, Start; or "Rest day" / "Done today, next is ..."), **I have X minutes**, week strip (tap to rest), level / XP / streak, knee care chip, history. The separate NEXT UP card is removed (Today says it). The Hyrox countdown is a small header on the Today card, not a second big card.

### 4. Never lose data

Current protections (keep): atomic writes, daily safety copy (newest 14), copy before any migration, damaged file moved aside and restored from the newest valid copy, data from a newer app never overwritten, in-memory vs disk guard when blocked, GitHub public sync never deletes local data.

Gaps found and the fix for each:

| Gap | Fix |
|---|---|
| Drive "Replace my data" overwrites with no copy; the daily copy may be hours old | Always write a labelled `pre-restore` safety copy first; restore defaults to **merge by id** (add missing sessions, keep newer edits); a full replace needs a second confirmation |
| Deleting a session is instant and permanent (copies reach back only 14 days) | Soft delete: move to a `trash` list for 90 days with Undo in the app; purge only after 90 days; GitHub's public copy is regenerated from the sessions on the phone, so a trashed session leaves it at once, but git history keeps it |
| A failed save (disk full, I/O error) is silent while memory shows the change | `save` returns a result; on failure show a clear banner and keep retrying; never mark a session as saved until the write succeeded |
| A mid-session crash or process kill may lose sets (to verify) | Autosave a draft after every completed set / step; on next launch offer "Resume" or "Save what I did" |
| Only 14 daily copies | Keep 14 daily + 12 weekly + every pre-migration / pre-restore copy |
| Nothing stops a bug dropping records | Shrink guard: a save that lowers the record count is refused (and a copy kept) unless it came from an explicit delete or restore action |

Rules for every future change:

- Records are append-only; ids never change. New fields have defaults.
- Any format change bumps `Store.CURRENT_SCHEMA` and ships a `Migration` with a test that loads a saved file from the previous version byte for byte.
- Plans are derived from records plus small stored facts (`Profile.planAdjustments`); never store a generated plan as truth.
- Tests for every write path: record count never drops without delete / restore; export of old data still opens.

## Phases (each its own PR, CI green first)

Other session types already save the moment they end; a mid-session draft for the timer-based ones is a later step.
0. (original list, for reference) **Data safety**: pre-restore copy and merge restore, soft delete + Undo, save-failure banner, shrink guard, weekly copies, draft autosave. Tests for each. (First, because everything else touches data.)
